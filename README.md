# LightPHI

LightPHI is a small, portable C++23 pen and tablet input interface. Its
`lightphi.input` module reports observed device capabilities and delivers
identified samples in bounded batches. Prediction corrections explicitly name
the sample they replace.

The source tree provides the contract, a deterministic fake backend, and the
first operating-system backend for current macOS.

## How backends work

Applications use one portable API regardless of the operating system. They
import `lightphi.backend` and link `LightPHI::LightPHI` and
`LightPHI::Backend`. CMake selects the backend from the target platform. There
is no backend option in application code and no runtime backend switch.

The backend implements `IInputSource`. It translates platform input into
`InputSample` and `InputBatch`, reports only capabilities observed from the
device, and calls the application's `IInputReceiver` synchronously. Platform
objects never appear in the public C++ modules.

On macOS, a Swift adapter owns the AppKit integration. It installs a local
`NSEvent` monitor on the application main thread, recognizes tablet events,
and converts AppKit values to plain coordinates, normalized pressure, radians,
timestamps, and capability bits. Swift passes those values through a private
C++ sink. A framework-free C++ Apple delivery core then assigns contact and
sample identities, manages the fixed queue, retries busy deliveries, and
handles cancellation and overflow.

Swift imports the private C++ sink through a Clang module map. C++ calls the
Swift adapter through the header generated by Swift's C++ interoperability
mode. This is compiled together in one CMake graph; LightPHI does not expose a
C ABI or Objective-C implementation layer.

Starting the current macOS source requires an active `NSApplication` and the
main thread. A command-line process without an application host receives
`InputSourceError::Unavailable`. The error is part of the portable API, so the
consumer still does not need to know which backend was selected.

## Build and test

LightPHI uses the header-only Microsoft Guidelines Support Library. A CMake
3.28 or newer build with a C++23 compiler and named-module support is
sufficient; CMake fetches the pinned GSL release.

Select a compiler with a matching `clang-scan-deps` through `CXX` or a CMake
toolchain file. On macOS, also provide the active SDK through
`CMAKE_OSX_SYSROOT`. The presets do not hard-code either machine-specific path.

```sh
just build          # release build, without tests or examples
just debug          # debug build, without tests
just debug-smoke    # debug build and fast tests
just debug-test     # debug build and all tests
```

Run `just` to list every command. The recipes are thin wrappers over the CMake
presets, so the equivalent works without `just`:

```sh
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

`just format` applies `.clang-format`, `just tidy-report` writes a clang-tidy
report, and `just test-asan`, `just test-ubsan` and `just test-tsan` run the
suite under the sanitizers.

This core/backend target split follows LightRHI. Backend contract tests use the
same automatically selected target as applications. A production backend never
falls back to the fake. The fake backend, examples, and tests default on for a
standalone checkout and off when LightPHI is added as a subdirectory.

## Testing a consumer without a device

Starting the macOS source needs a main thread with an active `NSApplication`, so it
cannot run in continuous integration. The fake source is how input-handling code
gets tested there. It is scripted rather than captured: a consumer enqueues the
batches it wants and decides when each is delivered, so a test can drive the busy
retry, rejection and overflow paths on demand. Nothing allocates after creation.

```cpp
import lightphi.backend.fake;

auto source{CreateFakeInputSource({.Capabilities = {...}, .MaximumQueuedBatches = 4U})};
(void)(*source)->Start(receiver);
(void)(*source)->Enqueue(batch);       // copies into fixed storage
(void)(*source)->DispatchNext();       // delivers synchronously, now
```

`examples/scripted_input.cpp` is a complete working version. Add LightPHI as a
subdirectory with `LIGHTPHI_BUILD_FAKE_BACKEND=ON` to get the target.

The macOS capability report is intentionally conservative:

| Capability | macOS source |
|---|---|
| Timestamp | Every captured `NSEvent` |
| Pressure | Current tablet proximity capability mask |
| Tilt | Both tablet tilt axes are reported |
| Twist | Tablet rotation is reported |
| Eraser | Current proximity identifies the eraser end |
| Coalescing, prediction, correction, hover | Absent; this backend does not deliver them |
